**Does your machine-learned potential have any long-range physics at all?**

Standard MLIP benchmarks score energies and forces on near-equilibrium structures. A model can reach an excellent
force MAE there and still be *completely blind* beyond its cutoff: no Coulomb tail, no response to a charge 12 Å
away, no idea that two anions repel. Those failures are invisible to an RMSE on a near-equilibrium test set, and
they are exactly what breaks a simulation of an electrolyte, an ion channel or a charged interface.

LongRangeBench measures them directly, with diagnostics that have a **known right answer**:

| diagnostic | a correct model | a model with no long-range term |
|---|---|---|
| tail fraction (d ≥ 8 Å) | **1** | **0** |
| normalised tail error ε | **0** | **−1** |
| fixed-charge ΔΔE slope | **1** | **0** |

So a number here is interpretable on its own, without a baseline to compare against. The harness proves this on
itself: the test suite scores a Lennard-Jones calculator against references generated by that same calculator and
asserts tail fraction 1.000; truncate the calculator's cutoff and it must read 0.000.

There are two ways in:

- **`lrbench eval`** — *how wrong* a model is, on fixed sets with fixed rules.
- **`lrbench priors`** — *whether it violates something that cannot be true of any correct potential*: twenty
  pass/fail checks of physical priors (far-field exponent, separability, F = −dE/dR, energy conservation,
  charge-state convexity), of the implementation (locality, response to total charge, determinism, precision) and of
  the evaluation itself (contamination, level of theory, whether a metric can even tell the model from a flat line).
  See [docs/priors.md](docs/priors.md).

```
| metric                                   | LJ, exact | LJ, 6 Å cutoff |
|------------------------------------------|-----------|----------------|
| tail fraction, ion_pair (d >= 8 A)       |     1.000 |          0.000 |
| normalised tail eps, ion_pair (d >= 8 A) |     0.000 |         -1.000 |
```

> **Status: alpha (v0.1.0).** The harness, metrics, model adapters and CLI are complete and tested. The reference
> datasets are being prepared for release — see [Data](#data) below. The API may still change; pin a commit.

## Install

```sh
git clone https://github.com/EricBoittier/LongRangeBench
cd LongRangeBench
pip install -e ".[plot,test]"          # core needs only numpy, scipy, ase
```

Extras: `hf` (HuggingFace datasets), `plot` (figures), `gguf`, `metatomic`, `cqr` (conformal quantile regression),
`viz` (chemiscope export), `test`. Model backends — PyTorch, JAX, mlip.cpp — are **not** dependencies: each model
family lives in its own environment and LongRangeBench shells out to it (see [docs/models.md](docs/models.md)).

## 60-second quickstart

No download, no GPU, no reference data required:

```sh
lrbench toy ./toy-data                                     # a self-contained set with LJ "DFT" references

# the same potential twice: once with a 40 A cutoff, once truncated at 6 A
lrbench eval --sets toy --data ./toy-data --normalise --out exact.json \
    --model 'ase:ase.calculators.lj:LennardJones?sigma=2.5&epsilon=0.05&rc=40.0'
lrbench eval --sets toy --data ./toy-data --normalise --out cut.json --label 'LJ, 6 A cutoff' \
    --model 'ase:ase.calculators.lj:LennardJones?sigma=2.5&epsilon=0.05&rc=6.0'
lrbench compare exact.json cut.json --md table.md --figdir figs/
```

The exact calculator scores tail fraction 1.000 and ε 0.000; the 6 Å one scores 0.000 and −1.000. That is the whole
idea of the benchmark, on a set small enough to read by hand.

Then point the same commands at real data and a real model:

```sh
lrbench eval --model "ase:lrbench.adapters:mace_polar?model='polar-1-m'" \
    --sets all --data ./lr-sets --normalise --conformal --equivariance --out polar.json
lrbench suite --models external --sets all --data ./lr-sets --outdir runs/ -- --normalise
```

## What it measures

| set | what it asks | headline metric |
|---|---|---|
| **dimers** | does E_int keep falling off like it should past the cutoff? | tail fraction, ε(r), offset-free error at 8 Å, \|E_int\| error ≥ 12 Å |
| **families_fixedq** | does a *distant* fixed charge change the local energy? | fixed-Q ΔΔE slope and MAE, per series |
| **families_full / _corrected** | the same for full charge rearrangement | ΔE / ΔΔE slope and MAE per series |
| **trimers** | is the three-body term there, or only pairs? | E3 MAE, geometry-relative ΔE3 |
| **charge parity** | do +1/−1 states of the same geometry behave consistently? | fragment-charge parity, scheme MAE, dipoles |
| **props** | are the multipoles and polarisabilities physical? | μ, Θ, α errors vs CP-SCF references |
| any set | is the model even invariant to what it should be? | rotation / reflection / translation / permutation errors |
| any set | does it know what it does not know? | Mondrian split-conformal and CQR coverage |
| any set | can you afford to run it? | ms/step, µs/atom/step, ns/day, peak GPU memory |

Design choices that make the numbers mean something — each is covered in [docs/metrics.md](docs/metrics.md):

- **Physics-normalised errors.** Errors are divided by a physical prior (the fragments' own DFT multipoles plus
  induction), signed, so ε = 0 is exact and ε = −1 is "the entire tail is missing". A meV number cannot tell you
  that; it just tells you which set you ran.
- **Charge and spin are part of the test.** Total charge, multiplicity and per-atom formal charges are passed to
  every backend that can take them, and a model that cannot accept them is *recorded as such* in the result rather
  than quietly scored as neutral.
- **Levels of theory are never pooled.** Every record carries its level; a group whose terms span levels is excluded,
  and an eval whose model level differs from the set's is refused unless you pass `--allow-level-mismatch` (which is
  then flagged in every table and figure).
- **DFT pathologies are excluded, not hidden.** Records flagged `dft_pathology_do_not_score`, and every group that
  touches one, are reported with the model's values under `pathology` and never scored.
- **Contamination is tracked.** `seen_by` flags per record, plus held-out-only and unseen-only rescoring, so a model
  trained on a set's pairs cannot quietly win on them.
- **Uncertainty is hierarchical.** 95 % intervals come from a bootstrap over scans/pairs (and ensemble members),
  not from treating correlated points along one scan as independent samples.
- **There is an oracle.** `oracle:multipole` scores the point-multipole energy of the two rigid fragments from their
  own DFT moments, truncated by rank. It is the achievable ceiling, so you can tell a model's failure from a metric's.

## Data

LongRangeBench is a harness; data comes from three places.

| source | status | licence |
|---|---|---|
| **toy LJ set** (`lrbench toy`) | ships with the repo, used by CI | CC0 |
| **canonical long-range sets** (dimers, families, trimers, charge parity, props) | `dimers`, `families_fixedq` and `trimers` are **public**: scores are committed in [results/](results/SUMMARY.md) and the structures are shown in the [explorer](https://ericboittier.github.io/LongRangeBench/explorer/). The full dataset is **moving to a public HuggingFace dataset**, with further sets to follow from CSCS | CC BY 4.0 |
| **external public QM sets** — GSCDB137 NC (45 subsets), NCI Atlas, BFDB biodimers, DES370K, SAPT10k, PLA15, Ko et al. 4G | converters included, you fetch the upstream data; nothing is redistributed here | each upstream's own licence |

Point `--data` at a directory of canonical `.jsonl` + `.groups.json` files, or use `--data hf` for the
HuggingFace dataset (`$LRBENCH_HF_REPO` overrides the repo id). See [docs/datasets.md](docs/datasets.md) for the
record schema, each external set's conversion path and its licence.

## Models

Anything with an ASE calculator can be scored, by import path, with no code in this repo:

```sh
lrbench eval --model "ase:my_package.calculators:MyPotential?cutoff=6.0" --sets dimers --data ./lr-sets
```

Also supported: metatomic / TorchScript exports — `mtt export`, i.e. most of the metatensor ecosystem, where the
level is inferred from the checkpoint name and the charge handling is read off the model's own
`requested_inputs()` rather than assumed — mlip.cpp GGUF models (`model.gguf`, via
`mlipcpp-eval`, the C API or the Python bindings), seed ensembles, and named released models — `so3lr`,
`so3lr-tauri{,-s,-l}`, `mace-h`, `mace-polar{,-l}`, `mace-omol`, `maceles-off`, `caceles-water`, `pet-omol-{s,m,l}`, `pet-spice-{s,l}`, `pet-mols-s`, `pet-omad-s`, `pet-mad` (`lrbench models`
lists them with their training level, licence and how charge/spin enter). `lrbench suite` runs several, each in its
own Python environment, and writes one combined table. See [docs/models.md](docs/models.md) and
[docs/adding-a-model.md](docs/adding-a-model.md).

## Notebooks

The diagnostics are also a [marimo](https://marimo.io) notebook, which is a Python file rather than JSON, so it
reviews and diffs like code:

```sh
marimo edit notebooks/long_range_diagnostics.py      # live, against your own runs/
marimo run  notebooks/long_range_diagnostics.py      # read-only app
```

[![Open in molab](https://marimo.io/shield.svg)](https://molab.marimo.io/github/EricBoittier/LongRangeBench/blob/main/notebooks/long_range_diagnostics.py)
runs it in the cloud with no install at all. The notebook in this repo is the **generator**: it carries the
diagnostics and the figures but no results, so opened cold it shows an empty state and waits for a `runs/`
directory. That is deliberate — the numbers for third-party models belong to whoever ran them, and a benchmark that
ships a frozen leaderboard inside its own notebook is a benchmark nobody can check.

To get a notebook with results in it, point it at your own `runs/`, or export a self-contained one:

```sh
lrbench eval --model <spec> --sets all --data ./lr-sets --out runs/mymodel.json
marimo export html-wasm notebooks/long_range_diagnostics.py --single-file -o site/index.html
```

The committed results, an explorer of every scored structure (`site/explorer/`, built with
`tools/build_chemiscope_views.py --rows results`) and this notebook (as WebAssembly) are published at
<https://ericboittier.github.io/LongRangeBench/> by `.github/workflows/pages.yml` on every push to `main`
(`tools/build_pages.py` renders `results/SUMMARY.md`; no raw result JSON is read).

The WASM export ([docs](https://docs.marimo.io/guides/wasm/)) is a single HTML file that runs the notebook in the
browser with no server, which is what the linked chemiscope views are built on.

## Commands

| command | what it does |
|---|---|
| `lrbench eval` | score a model or ensemble on one or more sets → `results.json` |
| `lrbench priors` | twenty pass/fail checks of physical, model and data assumptions (`--list` prints them) |
| `lrbench compare` | markdown / HTML tables and publication-style figures from several results |
| `lrbench suite` | one eval per model, each in its own environment, plus a combined table (local or Slurm) |
| `lrbench perf` | timing and memory on standard and generated boxes |
| `lrbench viz` | chemiscope export of a set with model errors as properties |
| `lrbench predict` | any model on any extxyz → a plain prediction JSON |
| `lrbench emulation` | DFT-emulation scores: fragment charges vs DFT rather than formal |
| `lrbench results` | add a validated result row or set card, check them, regenerate the tables ([docs/results.md](docs/results.md)) |
| `lrbench toy` / `models` / `sets` | write the toy set; list named models; list sets |

`lrbench <command> --help` documents every flag. Result JSON layout: [docs/output-schema.md](docs/output-schema.md).

## Contributing

Adding a model adapter or a dataset is the most useful thing you can do, and both are small, self-contained files —
see [CONTRIBUTING.md](CONTRIBUTING.md). Bug reports about a metric are especially welcome: if a diagnostic gives a
model an answer you can show is wrong, that is a bug in the benchmark, not in your model.
